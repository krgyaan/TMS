## 1. What This Project Is

### 1.1 The Real-World Problem
Imagine walking into a library every morning and being handed three stacks of legal papers, each between 50 and 400 pages long. Each stack represents an Indian Government or Public Sector Undertaking (PSU) **tender**—an open invitation by a government entity (like GAIL, IOCL, NTPC, or the Indian Railways) asking private companies to bid on contracts for engineering, solar installations, equipment procurement, or infrastructure projects.

To bid on these tenders, our company—**Volks Energie Pvt. Ltd. (VEPL)**—must read through hundreds of pages of dense legal and technical clauses before a strict deadline. A human bidding engineer, known as a **Tender Executive (TE)**, historically had to comb through every page looking for critical answers:
* How much money must we deposit up front just to bid? (Earnest Money Deposit or **EMD**)
* What percentage of the order value do we lose if delivery is delayed by a week? (Liquidated Damages / Price Reduction Schedule or **LD / PRS**)
* What percentage must we guarantee via a bank if we win? (Performance Bank Guarantee or **PBG**)
* What specific payment milestones apply? (e.g., 70% on material delivery, 20% on installation, 10% on commissioning)
* What previous work experience must we prove? (e.g., 3 completed orders of ₹1 Crore in the last 7 years)

Missing a single sentence buried on page 183 of an Additional Terms & Conditions (ATC) document could mean forfeiting a ₹50,00,000 bank guarantee or being disqualified from bidding after spending weeks on technical drawings. Doing this manually takes a Tender Executive 4 to 8 hours per tender, limits the number of tenders the company can bid on, and risks human error.

### 1.2 Who Uses This System
1. **Tender Executives (TEs):** Bidding engineers who review incoming tenders, evaluate whether our company qualifies, fill out technical sheets, prepare checklists of mandatory documents, and prepare price bids.
2. **Team Leaders (TLs) / Tender Approvers:** Senior managers who review the TE's findings, verify risks, and approve or reject proceeding with a bid.
3. **Operations & Finance Teams:** Project managers, accountants, and procurement officers who handle vendor work orders, purchase orders, client billings, bank guarantees, and cash flow tracking once a bid is won.

### 1.3 The Core Solution: TMS + VolksAI
The **Tender Management System (TMS)** is a complete enterprise web application paired with an intelligent extraction microservice called **VolksAI**.

When a Tender Executive uploads tender documents to the system:
1. **Inputs:**
   * **Primary Bid Document:** Standardized PDF from the **GeM** portal or PSU e-procurement site.
   * **Additional Terms and Conditions (ATC) / Scope of Work (SOW):** Secondary PDF containing custom clauses, special conditions of contract (SCC), and delivery milestones.
   * **Bill of Quantities (BOQ):** Equipment quantities and line-item schedules.
2. **Processing:**
   * VolksAI scans PDF text and uses fast, deterministic rule-based algorithms (Layer 1) to extract known standard tables.
   * If critical fields are missing or ambiguous, VolksAI invokes Anthropic Claude LLMs using tightly scoped snippets (Layer 2) to resolve exact legal wording without hallucination.
3. **Outputs:**
   * **Tender Information Sheet (Info Sheet):** Pre-filling commercial, financial, and technical parameters in the UI form with confidence badges and audit trails.
   * **Bidding Requirements Checklist:** AI-generated list of every mandatory compliance document required, paired with ready-to-download `.docx` annexure templates.

## 3. End-to-End Extraction Flow

1. **User Request:** TE clicks "Auto-Extract with AI" in `InfoSheetForm.tsx`.
2. **Controller:** `InfoSheetsController` calls `InfoSheetsService.autoExtractFromPdf()`.
3. **Hashing & Cache Check:** Computes SHA-256 hash of the PDF. If `'1.1.0:' + hash` exists in `tender_extractions` (and `force = false`), returns cached result in `less than 50ms` with **0 tokens**.
4. **Queue Dispatch:** If not cached, pushes job to BullMQ `pdf-extraction-queue`.
5. **Worker Execution:** `PdfExtractionProcessor` dispatches multipart PDF stream to `POST http://localhost:8001/extract`.
6. **VolksAI Processing:**
   * Text & layout extraction via PyMuPDF and pdfplumber.
   * Layer 1 deterministic regex matches standard tables.
   * Layer 2 invokes Claude Haiku 4.5 for missing fields and Claude Sonnet 5.5 for ambiguous clauses.
7. **Database Save:** Upserts extraction result in `tender_extractions` and records token cost in `claude_token_usage`.
8. **UI Hydration:** React polls job endpoint and populates the form with Green, Amber, and Red confidence badges.

## 4. The Claude & AI Subsystem

### 4.1 LLM Roles Architecture
* **Role 1 (`claude-haiku-4-5-20251001`):** Fast extraction of missing fields (`pbg_sd`, `payment_terms`, `prs_ld`, `bec_criteria`) using Anthropic Tool Use. Max 600 tokens (retry 1000).
* **Role 2 (`claude-sonnet-5-5`):** Resolves ambiguous clauses when general terms contradict special conditions (e.g. delivery or payment milestones), producing mandatory legal reasoning.
* **Role 3 (`claude-sonnet-5`):** Analyzes full page-tagged tender text (up to ~94k tokens) in `BiddingRequirementsService` to extract mandatory document checklists.

### 4.2 Scoped Context
VolksAI searches for section headings (e.g. `SPECIAL CONDITIONS OF CONTRACT`) and passes only targeted 500-2,500 character snippets to Claude. This saves 95%+ of token costs and eliminates "lost in the middle" attention failure.

## 5. Database Schemas

Managed via **Drizzle ORM** across 125 schema files.

### 5.1 Key AI Tables
1. **`tender_extractions`:** Stores the complete extracted JSON payload, confidence levels, clause excerpts, and SHA-256 hash version.
2. **`claude_token_usage`:** Financial ledger recording input tokens, output tokens, prompt cache hits, and USD costs per model.
3. **`bidding_requirements_jobs`:** Background job status and JSON checklists for Role 3.

<Info>
  <strong>Table Naming Distinction:</strong> <code>tender_infos</code> stores core tender metadata, while <code>tender_information</code> stores detailed info sheet parameters.
</Info>

## 6. Environment Configuration

* **`DATABASE_URL`:** PostgreSQL connection string.
* **`REDIS_HOST` / `REDIS_PORT`:** Redis queue connection.
* **`ANTHROPIC_API_KEY`:** Required for VolksAI Claude access.
* **`ANTHROPIC_ROLE1_MODEL`:** `claude-haiku-4-5-20251001`.
* **`ANTHROPIC_ROLE2_MODEL`:** `claude-sonnet-5-5`.
* **`CHILD_PDF_MAX_PAGES`:** `400` (supported page limit for ATC documents).
* **`AUTO_ENQUEUE_CHECKLIST_ANALYSIS`:** Controls background checklist triggering.

## 7. How to Run, Test and Debug

### Service Startup
```bash
# 1. Docker backing services
docker compose up -d postgres redis loki promtail grafana

# 2. VolksAI microservice
cd volksAi && python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

# 3. NestJS API backend
cd ../api && pnpm install && pnpm run db:migrate && pnpm start:dev

# 4. React web frontend
cd ../web && pnpm install && pnpm dev
```

### Automated Tests
* **API:** `cd api && pnpm test -- src/modules/tendering/info-sheets/pdf-extraction.spec.ts`
* **Web:** `cd web && pnpm test:unit`
* **VolksAI:** `cd volksAi && python -m pytest app/services/test_contact_integrity.py`
* **Model Ping:** `cd volksAi && python scratch/check_models.py`
